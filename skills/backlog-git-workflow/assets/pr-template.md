# プルリクエスト本文テンプレート

本文は端的にまとめる。レビュワーの負担を増やさないことを最優先し、コードや関連リンクを読めば分かることは書かない。

各言語ブロックの中で、概要を先に、変更の詳細を後に置く。

2言語で併記する場合は、英語のブロックを先に、もう一方の言語のブロックを後に置く。言語区切りの見出し（「English」「日本語」など）は付けず、各セクションの見出しをその言語で書くことで切り替える。1言語で運用しているチームは、下の骨組みの前半だけをその言語で書く。

Backlog記法のプロジェクトでは、見出しを `*` / `**` に、リンクを `[[label>url]]` に変換する（backlog-notation スキル参照）。チェックリスト `- [ ]` はプルリクエスト本文では機能しないので、箇条書き `-` を使う。

## 骨組み

```markdown
## Overview

- <Why this change exists: what it unblocks, prevents or fixes, and for whom. Name the issue it serves>
- <What this change does, and if phased, how far this PR goes>
- <Impact: whether behavior changes now, or is gated behind a disabled flag>

## Changes

- <path>: <the key decision behind this change, not a summary of the diff>
- <path>: <same>

## Notes for review

- <what to look at closely, or what to watch out for when applying>

## 概要

- <何のための変更か。何が前に進むか、何を防ぐか、誰のためか。対応する課題キーを示す>
- <この変更で何をするか。フェーズ分割している場合はこのプルリクエストがどこまでか>
- <影響範囲。動作が変わるか、フラグで無効化されているか>

## 変更点

- <path>: <この変更での重要な設計判断のみ。差分を読めば分かることは書かない>
- <path>: <同上>

## レビュー観点

- <特に見てほしい点、または適用時の注意>
```

Terraform を扱う変更では、上記の末尾に `## Plan` セクションを追加し、対象環境の `terraform plan` 実行結果をコードブロックで貼る。プレーンテキストなので言語ブロックには含めず1つだけ置く。差分がない環境は列挙しない。

## 書き方

Overview / Changes / Notes for review（概要 / 変更点 / レビュー観点）は、それぞれ箇条書き3点以内にする。4点目以降の情報は本文から落とす。レビュアーが最初に知りたいこと（何が変わるか、今すぐ動き出すのか）を優先し、それ以外は削る。

Overview / 概要 の 1 点目は目的にする。レビュアーが最初に判断するのは「この変更は要るのか」で、差分からは読み取れない。何が前に進むか、何を防ぐか、誰のためかを 1〜2 文で書き、判断の根拠になる実測値があれば数値を添える。「この課題の例外条件を足す」のように課題名を言い換えただけの書き方にしない。

目的は書くが、経緯は書かない。どういう議論があったか、前は何を試したか、レビューで何を指摘されたかは、読み手の判断を変えないので落とす。関連するプルリクエストやドキュメントを読めば追える場合は、それを書き写さず参照だけを示す。参照は課題キー（`PROJ-100`）か `[題名](絶対URL)` の形で書き、URL やファイル名だけを並べない。前フェーズからの申し送りは課題本文の役割（backlog-create-issue 参照）で、プルリクエスト本文の役割ではない。

デプロイ手順は書かない。デプロイの実行や確認は別の運用ドキュメント・Runbookの役割。

変更点には重要な設計判断があるものだけを挙げる。ファイル名を並べるだけでは差分を読めば分かるので、そのファイルで何を決めたかを書く。既存のパターンから外れた選択をしたなら、外した理由を添える。

両言語のブロックは同じ構成の見出しを立て、対応する内容を書く。片方にしかない情報を作らない。

絵文字は使わない。Backlog API が4バイト UTF-8 を拒否する。
