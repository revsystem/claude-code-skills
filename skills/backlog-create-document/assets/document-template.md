# ドキュメント本文テンプレート

ヘッダ、範囲、本文の節、未決事項の順に置く。ヘッダの行と本文の節は、内容があるものだけを残す。

## 骨組み

```markdown
課題: [PROJ-123](https://<space>/view/PROJ-123)（<この文書が答える作業の位置づけ>）
前提: [<題名>](<URL>)（<そこから何を前提にするか>）、[<題名>](<URL>)（<同>）
手順: [<手順書の題名>](<URL>)
関連: [<題名>](<URL>)
別紙: [<別紙の題名>](<URL>)

<この文書が定めること、または記録することを1文。前提の資料にあるものはここでは持たない、と持たないものを1文>

## 現在の状態

<判断の出発点になる事実。判断に効く数値だけを置く>

## <読者の問い1に答える節>

<1文目にこの節の結論。2文目以降はその根拠>

## <読者の問い2に答える節>

<同>

## 担当

<誰が何を決め、誰が何を実行するか>

## 未決事項

- <決まっていないこと>。<決める時期と担当>
```

## ヘッダ

ヘッダは、この文書を開いた人が「どこから来て、何を前提に読めばよいか」を最初の数行で掴むためにある。各行の役割は次のとおり。

| ラベル | 置くもの | 省略 |
|---|---|---|
| `課題:` | この文書を成果物とする課題。括弧で課題の中での位置づけ（何番目の作業か、何の判断材料か） | 不可 |
| `前提:` | この文書の判断の根拠になる資料（調査結果、設計）。括弧で、その資料から何を前提にするか | 前提が無ければ省く |
| `手順:` | この文書の判断を実行するときに使う手順書。この文書に合わせて手順書の更新が要るなら、その旨を未決事項に書く | 手順が別に無ければ省く |
| `関連:` | 前提ではないが合わせて読むと分かる資料や、この文書の判断を実行する後続の課題 | 無ければ省く |
| `別紙:` | この文書から切り出した全量の表や個別の判定 | 別紙が無ければ省く |

リンク名は資料の題名にする。URL やファイル名をそのまま見せない。リポジトリ内のファイルを指す場合は、既定ブランチにマージ済みのファイルの URL を使う（backlog-git-workflow の「成果物へのリンク」）。

## 範囲

ヘッダの直後の1〜2文で、この文書が何を持ち、何を持たないかを宣言する。

```markdown
夜間バッチが失敗したときに、自動で再実行するか担当者が判断するかを原因別に定める。失敗ごとの記録と通常の運用手順は前提の2文書にあり、本書は再実行の判断だけを持つ。
```

持たないものを書いておくと、前提の資料の内容を本文に写したくなったときの歯止めになる。

## 本文の節

見出しは読者の問いに対応させる（「何を自動で再実行するか」「いつ自動再実行を止めるか」「データ不整合のときはどうするか」）。作業の順序（「調査」「分析」「結果」）では立てない。

節の1文目にその節の結論を書く。読者が1文目だけを拾い読みしても判断が分かる状態にする。表を置く節では、1文目を結論の要点だけにして、個々の値は表に任せる。

当初の方針を変えた場合は、本文の最初の節で「何から何に変えたか」と変えた理由を書く。理由は根拠ごとに1段落にする。

## 担当と未決事項

担当は、決める人と実行する人を分けて書く。決まっていない場合は未決事項に回す。

未決事項は、決まっていないことと、いつ誰が決めるかを1行で書く。決める時期が書けない項目は、何が揃えば決められるかを書く。
