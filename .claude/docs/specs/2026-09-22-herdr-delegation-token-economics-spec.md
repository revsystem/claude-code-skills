# delegating-to-herdr-agents トークン経済観点の追加 設計仕様

日時: 2026-09-22

## 目的・背景

herdr で複数エージェントに役割を分担させる価値は、探索や読み込みのトークンを各エージェントのコンテキストに閉じ込め、司令塔には結論だけを返させることにある。現状の delegating-to-herdr-agents は「誰に何を頼み、どう検証して統合するか」は持っているが、「そもそも何を委譲すると得なのか」を持っていない。この判断基準を追加し、作業の形から役割分担が自然に選ばれるようにする。

### herdr スキルとの関係

herdr スキルの description にある「Do not use merely because a task could benefit from a background terminal, delegation, or parallel work」は、ユーザーが求めていないのにペイン制御スキルをロードして端末を掴むことを防ぐ発動条件であり、役割分担という進め方を否定するものではない。delegating-to-herdr-agents は「CLI の権威は herdr スキル、こちらは分担の進め方だけ」と既に切り分けており、両者は競合していない。

したがって本件で解くべきは herdr スキルとの調整ではなく、delegating-to-herdr-agents 自身に欠けている次元の補完である。

### 変更してはいけない場所

`~/.claude/skills/herdr/SKILL.md` は upstream（herdrdev/herdr、refs/tags/v0.9.1）のコピーで、`gh skill` 管理下にありこのリポジトリの `skills/` に含まれない。編集しても更新で上書きされる。変更はすべて `skills/delegating-to-herdr-agents/SKILL.md` に閉じる。

## スコープ

含めること:

- 委譲判断の基準（入力が大きく出力が小さい仕事を委譲する）の明文化
- 委譲してはいけない仕事の明示
- description の拡張による、作業の形からの発動
- 分担表への委譲理由列の追加
- モデル・エフォートの決め方を役割名から仕事の形へ変更
- 分担案を提示して止まる節の追加
- 返し方を出力サイズで分ける規則の明確化
- 指摘の検証を比例させる規則の追加

含めないこと:

- herdr スキル本体の変更
- herdr CLI の使い方の記述（権威は herdr スキルに置いたままとする）
- Agent ツール（Claude Code のサブエージェント）との使い分けの一般論。グローバル CLAUDE.md の記述に委ねる

## 設計

### 委譲判断の基準

入力が大きく出力が小さい仕事を委譲する。探索・横断検索・広い読み込みを伴い、返るのが結論や指摘に収まるものが該当する。委譲によってその探索トークンは相手のコンテキストに留まり、司令塔には要約だけが入る。

逆に入力が小さく出力が大きい仕事（仕様から長文を新規に書き起こす等）は、委譲しても司令塔側の消費は減らない。依頼文の作成と結果の検証が上乗せされる分、単純に損になる。

委譲しない仕事として次を明示する。グローバル CLAUDE.md の「通読が必要な品質レビューは委譲しない」を herdr の分担にも適用する。

- 原稿全体の一貫性チェック、章をまたいだ表現の重複検出
- 設定ファイル群のように、全体を見渡して初めて判断できる見直し
- 分割すると繰り返しや直し漏れが視界から外れる種類の作業

### description の拡張

現状の description は「分担して」「レビューを頼んで」という明示依頼にのみ反応する。作業の形でも反応するよう、独立した読み込み量の多い枝が複数ある場合と、実装とは独立したレビューが要る場合を trigger に加える。

発動が広がっても勝手に動き出すことはない。既存の役割分担ゲート（分担表をユーザーに確認するまで pane split も agent start も agent prompt もしない）がそのままブレーキとして機能する。description が広げるのはロードであり、行動ではない。

### 分担案を提示して止まる

作業の形が上記の基準を満たしたとき、ユーザーからの明示依頼が無くても分担案を提示してよい。提示するのは分担表と、その分担で何が減るかの一文まで。承認を得るまで起動も依頼も行わない。

### 分担表への委譲理由列

役割名だけでは基準が効かないため、委譲理由の列を追加する。なぜ自分でやらずそのペインに出すのか（探索範囲が広い、担当が独立している、別種の目で見たい）を書かせることで、判断基準が表の形で残る。

### モデルとエフォート

現状の「役割から決め」を「仕事の形から決め」に置き換える。

- 広く浅く探す、候補を集める、機械的に洗う: 安いモデル・低いエフォート
- 設計判断、最終レビュー、統合の可否判断: 強いモデル・高いエフォート

役割名とコストを固定で対応させない。同じ「調査担当」でも、全文検索の刈り取りと設計上の是非の検討ではかける費用が違う。

### 返し方を出力サイズで分ける

現状は既定で `agent read --lines 120` を司令塔に流し込み、ファイル出力の要求を失敗例として挙げている。これはユーザーの可視性を優先した設計で、トークンを節約する目的と正面からぶつかる。ルールを反転させるのではなく、境界を出力サイズで切る。

- 短い回答（レビュー指摘、可否の判断、数件の発見）: ペインから読む。ユーザーが同じ画面で経緯を追える利点が上回る
- 長い成果物（調査メモ、レポート、一覧）: 出力先の絶対パスを渡し、書いたらパスだけ返させる。司令塔は必要な節だけ読む

既存の記述は同じ趣旨を持つが「成果物として残す依頼のときだけ」という条件で書かれており、長さによる線引きになっていない。判断の軸を出力サイズに統一する。

### 検証を比例させる

「相手の回答は untrusted input として扱い、自分でファイルと行番号を確認してから採用する」を全件に適用すると、節約分が検証コストで消える。検証の範囲を次に限定する。

- 確認するのは引用された行とその周辺であって、ファイル全体ではない
- 対象は自分の行動を変える指摘。採用しないと決めた指摘は裏取りしない
- 相手が根拠の位置を示さなかった指摘は、検証せずに差し戻す

## 検証

スキルファイルはセッション開始時にキャッシュされるため、description 変更による発動は新しいセッションでのみ確認できる。編集したセッション内での確認結果は根拠にならない。

確認項目:

- 新セッションで、明示的な分担依頼を含まない読み込み量の多い並行作業の相談に対し、スキルがロードされ分担案の提示で止まること
- 分担案の提示が、起動・依頼・ファイル編集のいずれにも先行していること
- 分担表に委譲理由列が含まれること
